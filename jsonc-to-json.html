Why a file that opens fine refuses to parse

Strict JSON has no comment syntax. The grammar defines strings, numbers, the literals true, false and null, and the six structural characters — and that is the whole list. A // is not in it, so the parser stops there and reports an error, which is why a tsconfig.json that your editor happily displays can fail the moment JSON.parse sees it.

Nothing is wrong with the file, and nothing is wrong with the parser. Two different languages are involved: the editor reads JSONC, and your code reads JSON. VS Code reads tsconfig.json, .vscode/settings.json, devcontainer.json and similar files as JSONC, so it strips the comments as it loads them and never shows you the difference.

What JSONC actually allows

Two relaxations and no more:

  • Comments — both // line comments and /* block comments */. They are allowed wherever whitespace is allowed, including after the last property, between a key and its colon, and inside a container that has no properties at all.
  • Trailing commas — a comma after the final element of an object or an array, with any amount of whitespace or a newline before the closing bracket.

Everything else is unchanged from JSON: strings and property names use double quotes, numbers keep the JSON grammar, and there is no undefined, no NaN and no leading plus sign. That is the difference from JSON5, which is a much larger superset and is treated separately below.

The trap this tool has to avoid

Stripping comments looks like a one-line regular expression, and that version is unsafe on real payloads. A double slash appears inside perfectly ordinary string values — every https URL has one, and "https://example.com//path" even has two. Run //[^\n]* over it and the rest of the line is deleted, turning a valid document into an unterminated string, or worse, into a shorter one that still parses with a value quietly truncated.

So the conversion here walks the text character by character and tracks whether it is inside a string, honouring backslash escapes. A comment marker only counts when it appears outside a string, which is the only place JSONC allows it. Whitespace inside a string is never touched, and if the document already parses as strict JSON the tool says so and changes nothing.

JSONC and JSON5 are not the same file

JSON5 is where people usually land after this problem, and it is a much bigger dialect: single-quoted strings, unquoted keys, hexadecimal numbers, + signs, leading and trailing decimal points, Infinity, NaN, multi-line strings and additional escapes. Converting JSON5 by deletion is not safe, because several of those forms carry values that JSON cannot represent at all — NaN has no JSON counterpart, and Infinity needs a decision, not a rewrite.

This page therefore refuses them. If the text is not JSON plus comments and trailing commas, the conversion fails and says which category the remaining problem belongs to, instead of inventing a value.

Reading it as JSON fails where the comment is

There is nothing subtle about the failure, which is what makes it easy to confirm. Read a commented tsconfig.json with the strict reader and it stops at the first comment:

node -e "JSON.parse(require('fs').readFileSync('tsconfig.json','utf8'))"

SyntaxError: Expected property name or '}' in JSON at position 4
             (line 2 column 3)

That position is the comment, not the data. The value on line 3 parses perfectly well; the parser never reaches it. Running the same command against a comment-free file prints the object and exits silently, which is the control that tells the two cases apart.

The tools that own these formats already handle it, and that is why the file got written this way in the first place — tsc reads tsconfig.json through its own JSONC parser, and VS Code reads its configuration files the same way, so neither of them ever reports a problem. Only code that later opens the file as data hits the wall.

The durable fix is to keep the comment-carrying file as the source of truth for humans and emit a strict copy for machines, rather than teaching a service to read a relaxed dialect. Two systems reading one file with two different parsers is how a trailing comma becomes a production incident.

Frequently Asked Questions

What is JSONC?

JSONC is JSON with two relaxations: comments and trailing commas. Nothing else changes — strings still need double quotes, keys still need double quotes, and the value types are the same. It is the dialect used by tsconfig.json, .vscode/settings.json, devcontainer.json and other Microsoft-family configuration files.

Why does JSON.parse reject a file that works in my editor?

Because the editor is not using JSON.parse. VS Code reads configuration files as JSONC and strips the comments as it loads them, so a trailing comma or a // line is invisible to you. Every strict parser — JSON.parse in the browser, json.loads in Python, json_decode in PHP — stops at the first comment, because the JSON grammar defines no comment token at all.

Is JSONC the same as JSON5?

No. JSONC is JSON plus comments and trailing commas, and it is deliberately small. JSON5 is a much larger superset: comments, trailing commas, single-quoted strings, unquoted keys, hexadecimal numbers, leading and trailing decimal points, a leading plus sign, Infinity, NaN, multi-line strings and escaping rules. A JSON5 document often cannot be converted by stripping syntax, because its values are not JSON values.

Does this tool change my data?

No. It removes comments and trailing commas, and it reports what it removed. Comments carry no value in JSON, and trailing commas only ever separate values that are already separated, so the parsed result is identical. Whitespace inside a string is data and is never touched — which matters for URLs, where a double slash is part of the address rather than the start of a comment.

Can I stop strict JSON from rejecting comments instead?

Only by changing the reader, and that is usually the wrong direction. A JSONC parser in production means two services reading the same file can disagree about what it says. The durable fix is to convert the file to strict JSON at build time — which is exactly what TypeScript, VS Code and the other tools do with their own configuration files.

What will this tool not convert?

Anything that is not JSON plus comments and trailing commas. Single-quoted strings, unquoted property names, NaN, Infinity, hexadecimal numbers and multi-line strings are all rejected after conversion rather than quietly rewritten, because those changes would alter values rather than syntax. For errors of that kind, use the validator, which names the cause and the line.

It is not a validator, and it will not call a comment-carrying document valid: the parser itself still rejects those characters, which is what the known limits describe.
